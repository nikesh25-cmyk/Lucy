# Evidence gaps become linked follow-up work

An accepted gallery contribution can become a new task in the same mission. A human mission owner with reviewer privileges, or an administrator, specifies the follow-up title, deliverable/evidence requirements, rights and approved source hosts. The mission must be open (or a practice demonstration), and the origin must still be accepted with an accepted human review record. The new task inherits the mission beneficiary, reviewer and acceptance criteria; it does not inherit acceptance from its origin.

The gallery form starts from the brief’s unresolved evidence text. The owner should replace broad gaps with a specific deliverable, supporting locations, applicability checks and uncertainty requirements. Existing source-host permissions are offered for review. No agent automatically creates or approves follow-ups, and an evidence gap does not authorize contacting a producer, buyer or institution.

`POST /api/v1/tasks/follow-up` accepts `submission_id`, `title`, `instructions`, `rights`, `allowed_domains` and an `Idempotency-Key` header. The server selects the original mission, enforces owner/admin permission and current acceptance, creates the task and its relation atomically, and records an audit event. Retrying the same key/payload returns the same task; changing the payload returns 409. The browser keeps a key for that form so a failed refresh can be retried without duplicate task creation. Runtime credentials and public visitors cannot create linked tasks.

The Missions view shows the originating submission ID/version and current source status. A still-accepted source offers its downloadable briefing. If the source is later quarantined, the link disappears and its changed status is visible. Existing follow-up tasks are retained rather than silently rewritten; their mission owner must assess whether to pause or revise work. Follow-up instructions remain the owner’s scoped request, not a declaration that the source is true. Normal claim leases, submissions, independent review and adoption govern the new task.

Schema 7 adds `task_followups` with references to tasks/submissions/creator accounts, retry-key uniqueness and a payload fingerprint. Opening schema 6 adds the table without replacing old records. Recovery accepts versions 1–7, checks schema-seven storage and references, and validates the audit chain. Account export becomes `shared-world-account-v7` and includes follow-up tasks created by that account; public task metadata omits retry keys, fingerprints and creator IDs. Existing account deletion anonymizes the retained account record while shared mission work remains.

Verification: 156 tests passed. Tests cover version-two origin persistence, mission/reviewer inheritance, duplicate retry refusal, unrelated reviewer/member/runtime refusal, source-host validation, paused/quarantined refusal without orphan tasks, ordinary follow-up claim/submission/independent review, owned export, restart/audit validation, schema-six migration, incomplete schema-seven recovery refusal and HTTP creation/visitor refusal. Actual isolated browser QA created a scoped carrier-cost fixture from a reviewed fictional brief and verified its mission, approved host, source version and claim control. No production account or actual quote was created.
