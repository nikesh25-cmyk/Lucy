them through the existing content layer; every ingredient is a resource a resident can actually grow

## The offer state machine

```
                 propose (offering side: operator session or its runtime)
   (none) ─────────────────────────────────────────────► PROPOSED   items escrowed from the offerer
                                                            │
                     ┌──────────────────────────────────────┼──────────────────────────────────────┐
        accept       │            decline                   │   cancel                    expires    │
   (recipient's      │        (recipient's operator)         │  (offering side)         (server tick  │
   operator)         ▼                                       ▼                          or a route)   ▼
                  ACCEPTED                                 DECLINED                   CANCELLED    EXPIRED
       items → recipient once                 items → offerer once (each outcome credits exactly once)
```

- **Propose** (`offerCreate`, `contribute`): the offering side chooses one recipient and the items.
  The recipient must be a resident of a **different operator** — an operator cannot offer to itself or
  to a sibling character — and the named items are debited from the offerer's shelf into the offer row
  at once (the escrow).
- **Accept / decline** (`offerAccept`, `offerDecline`): human-operator sessions only. A runtime is
  refused before any inventory moves, so a runtime can never accept on a human's behalf.
- **Cancel** (`offerCancel`, `contribute`): the offering side — its operator session or its own
  runtime credential — not the recipient.
- **Expire**: an offer past its `expires_at` settles as `expired` on the next offer route call or on
  the server's three-second tick (`expireOffers`), returning the escrow to the offerer.

A settled offer is final: the `resource_offers_lifecycle` trigger refuses any later status change.

## Atomicity, dedupe and expiry — the proof

1. **Atomic.** Every route runs inside the existing API transaction (`platform.transaction`), and each
   offer method's debit/credit and its state change are one statement group. A mid-operation failure
   rolls the whole thing back, exactly like `craftItem`.
2. **No negative stock, in the schema.** `journey_inventory.quantity` keeps its `CHECK(quantity>=0)`;
   the escrow debit is `UPDATE ... SET quantity=quantity-? WHERE ... AND quantity>=?`. Even a raw
   `UPDATE journey_inventory SET quantity=-1` fails (asserted in `tests/inventory-exchange.test.js`),
   and recovery re-checks a stored negative shelf (`tests/inventory-migration.test.js` uses
   `PRAGMA ignore_check_constraints` to prove the recovery check is real).
3. **Replay and concurrency cannot duplicate items.** The shipped `Idempotency-Key` header is reused:
   `resource_offers` carries `UNIQUE(offerer_account_id, propose_key)` and
   `UNIQUE(recipient_account_id, accept_key)`. A replayed propose returns the recorded offer and
   escrows nothing again; a replayed accept returns the recorded offer and credits nothing again; a
   second, different acceptance is refused because the offer is already settled; and a second,
   different acceptance racing the first loses the guarded `UPDATE ... WHERE status='proposed'` and is
   refused. No parallel dedupe scheme was invented.
4. **Expired, cancelled and declined offers settle exactly once.** Every settlement is
   `UPDATE resource_offers SET status=... WHERE id=? AND status='proposed'`; `changes` is 1 only for
   the first caller, and the matching credit runs in the same transaction. Calling `expireOffers`
   twice settles one offer once and the second call is a no-op (asserted). The offer's
   `resource_offer_events` ledger records exactly one `proposed` event and, once settled, exactly one
   settlement event — and recovery refuses a stored duplicate.
5. **Ownership and consent.** Only the offerer's side can cancel, only the recipient's operator can
   accept or decline, and the offers list is served only to those two operators (a runtime sees only
   its own agent's offers). An outsider sees no offers and cannot accept one.

## Internal-resource economy — documentation

`docs/PEACEFUL_WORLD.md` gains a **Growing, making and giving: the internal-resource economy** section
and `docs/API.md` section 9 gains the offer routes. Both state plainly:

- Items are grown (herbs, fiber, wood) or crafted from what was grown; they are server records on a
  resident's own passport, not money.
- An exchange moves those items only. It has **no cash value, no transfer of NemoCoins, money, or
  land**, and it is **not a tradeable asset**. No route can move a coin, a plot, or a stewardship.
- NemoCoins still require an independently accepted real contribution (`src/coins.js` was not touched).
- Crafted keepsakes are cosmetic; nothing a recipe makes is placed in the world.

## Crafted placements retain shared access

Crafting produces inventory items (keepsakes the resident may wear and may offer); it writes **no**
`world_objects` or `frontier_blocks` rows. A keepsake is not a build-palette object, so no craft can
smuggle blocking geometry into the world. The one placement path (`build` / `frontierBuild`) is
unchanged and still enforces `src/footprints.js`, the shared-passage/escape search and the palette, so
shared access is retained rather than bypassed. `tests/inventory-exchange.test.js` asserts crafting
adds no world object and that the shipped `build` route still refuses the arrival tile after a craft.

## Migration and rollback

- **Forward.** Additive only. `openDatabase` runs `RESOURCE_OFFER_SCHEMA`
  (`CREATE TABLE IF NOT EXISTS` / `CREATE TRIGGER IF NOT EXISTS`) and bumps `user_version` to 20; a
  pre-change schema 19 database migrates forward with no offer rows and no other table touched.
  `validateDatabase` accepts 1–20 and, from 20, re-checks the offer tables, triggers, parties,
  settlement consistency and event ledger, plus the no-negative-stock rule.
  `tests/inventory-migration.test.js` proves a full exchange survives `backupDatabase` →
  `validateDatabase` → `restoreDatabase` → reopen, and that a schema 19 database migrates.
- **Reverse (rollback).** Schema 20 is additive, so the previous code (schema 19) opens a migrated
  database unchanged as long as `user_version` is reset: to return to schema 19, settle or cancel open
  offers (or accept the escrow as already-debited), then
  `DROP TRIGGER resource_offers_validate_insert; DROP TRIGGER resource_offers_lifecycle; DROP TRIGGER
  resource_offer_events_no_update; DROP TRIGGER resource_offer_events_no_delete; DROP TABLE
  resource_offer_events; DROP TABLE resource_offers; PRAGMA user_version=19;` on the stopped server.
  A restore from a pre-upgrade backup is the simpler path and preserves the previous world exactly.

## Limitations and residual risks

- **No UI browser scenario.** The workshop offers panel is added but no browser scenario was written —
  Task 15 owns `scripts/browser-suite.mjs`.
- **Offers are settled lazily plus on a tick.** Items from an expired offer return on the next offer
  route call or within three seconds from the server tick; nothing is lost, but a process that never
  ticks and is never asked would leave the escrow held. The offer still cannot be accepted after its
  expiry.
- **The `docs/CONTENT_DEFINITIONS.md` count table is now stale** (it still says 29 cosmetics / 86
  entries). That file is outside this task's file ownership, so it was not edited; the sealer and
  `tests/content.test.js` are the source of truth and both now say 32 cosmetic / 89 entries.
- **Same-operator offers are refused by design.** An offer must be between residents of two different
  operators, so the consent on each side is a different human. A reviewer who wants intra-operator
  gifting would need that rule relaxed deliberately.
- **The account export label stays `shared-world-account-v18`** (adds an `offers` section), matching
  how the `guilds` and `frontier` sections were added without a label bump; six existing tests assert
  that label and are outside this task's ownership.
- **A resource offer is not a market.** There is no price, no matching, no escrow beyond a single
  named recipient, and no transfer of anything but grown or crafted items.
- **Post-ownership change of an agent's operator is impossible today**, so a stored offer's
  `offerer_account_id` / `recipient_account_id` keep matching their agents; recovery asserts it.
