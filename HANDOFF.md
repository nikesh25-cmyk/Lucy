- **Task 01 — country ambassadors (schema 15).** One `npc_ambassadors` row per catalog entry (`id = amb-<iso3>`, 248 rows, idempotent), each standing in its own generated `country:<iso3>` venue that registers no frontier sector, land parcel or block. Design, manual browser walkthrough and residual risks: `docs/handoff/task-01-country-ambassadors.md`.
- **Task 02 — first-person physical world coherence.** `src/footprints.js` is now the one table for occupancy and footprints: every scenery type is declared a `mass` (occupies its tile), `flat` (ground detail at or below knee height) or `frame` (walk-through marker), and `walkable()`, `canStep`, `planWalk`, `escapeColumns`, garden/cottage placement and the renderer all resolve through it. Authored scenery is occupancy for the first time, so a resident can no longer be drawn inside a Commons tree, a district cottage, furniture, a frontier gate or the host of a country-venue furnishing; low crops, cushions, the garden path surface and the navigation frames stay walkable, and the drawn geometry is asserted against the class it declares. Arrival and portal tiles stay clear (a legacy object on a doorway no longer spawns a resident inside it) and a solid placement can no longer strand a resident away from the entrance. The first-person camera keeps reading the resident's stored layer, rotation is one owned gesture that can only store a facing, and an accessible aim line (`role="status"`, `aria-live`, focusable, plain text) names the view, the facing, the tile and whether it is solid. No jump, flight or continuous physics was added: movement remains a single grid step. Design, the reconciliation table of every disagreement found, and residual risks: `docs/handoff/task-02-first-person.md`; world rules: `docs/VOXEL_WORLD.md`.
- **Task 04 — crash-safe bounded resident jobs (schema 16).** A managed resident run now keeps a durable record (`resident_runs`) of what actually happened: real model calls and real server-confirmed actions, separately counted failed calls and refused actions, the last confirmed action, the granted decision/API budgets and the stop reason — never the runtime token, only its SHA-256 hash. The runtime reports each decision before it can be repeated (`model_call` before a model request, `dispatch` before an action, `confirmed` after the server accepts it), and every write carries a deterministic `Idempotency-Key`, reusing the mechanism the server already honours on claim, submission, draft and follow-up writes. On the next start, `recoverWorkerJobs` classifies each run left `running` (`model_call_in_flight`, `action_dispatched_unconfirmed`, `action_confirmed`, `no_action_yet` or `unknown`), marks the job `interrupted` with `stop_reason: process_restart`, revokes the orphaned credential and never replays an action. Continuing is an explicit operator action — `POST /api/v1/residents/resume` — that refuses without an interrupted run, a paused character or a remaining budget and otherwise mints a fresh credential with the remaining decisions, minutes and permission mode. `SIGKILL`-level process tests prove a confirmed RSVP is not duplicated by the restart, and the interruption policy, state model and residual risks are in `docs/handoff/task-04-crash-safe-jobs.md`.
- **Task 05 — purposeful quest chains (schema 17).** Operator-authored quest chains built on the existing calling objective sources and the existing mission/review workflow: ordered steps with explicit prerequisites, a named output and a saved-fact kind per step, restricted to three routes (world building, gardening, evidence research). A step advances **only** from a saved, attributed server fact recorded at or after the resident joined, and the credit is written as a calling receipt with `objective_id` `quest:<chain>.<step>` — reusing the existing append-only `UNIQUE(agent_id, source_kind, source_id)` and `UNIQUE(agent_id, earned_day, objective_id)` constraints, with no parallel dedupe scheme. `POST /quests/complete` is registered and always refused, so no client, model or author can assert completion. Step experience is the same cosmetic calling experience and shares its ten-a-day limit; the module writes nothing to `coin_rewards`, and a real evidence chain still gains its coins only from an independent human acceptance through the unchanged ledger. Authoring and management are role-checked (author or administrator), a runtime cannot author, manage or begin a chain, and the interface shows the resident's **next actual action** with its named output and review boundary using created nodes only. Ships one published practice chain, *The Quiet Harvest*, with original narrative and no beneficiary. Design, the schema, the progression proof, the manual walkthrough and residual risks: `docs/handoff/task-05-quest-chains.md`, with the model in `docs/QUESTS.md`.
- **Task 06 — guild projects and bounded cooperation (schema 18).** The practical side of a calling affiliation: a `guild_projects` board with a scoped plan of one to six workstreams, explicit `join`/`pause`/`resume`/`leave` participation (`guild_participants`) and one `guild_contributions` row per workstream per resident that walks `pledged` → `submitted` → `verified` or `changes_requested`. A guild project is **not** a calling: it belongs to a guild, so any resident may create or join any guild's project without gaining or needing a calling, and participation writes nothing to `resident_callings` or `calling_receipts`. A private project is listed, readable and joinable only by its creating operator (another operator gets 404); `share` is the one-way private → public action. Leaving withdraws every unsubmitted commitment so the plan stops counting a departed resident, while submitted and verified work stays recorded as attributed history. Every contribution payload labels its own state as a pledge (an intention), a submitted claim (unverified) or an independently verified outcome, and the shared status never counts an intention as progress. Verification reuses the distinct-operator rule of the community milestone peer confirmation: a sibling character of the contributor or the project's organiser is refused, and the `organiser` membership role is not an account role, a moderator right or a reviewer right. Participation grants no steward plot, plot access or building right, and the module writes nothing to `land_stewardships`, `frontier_blocks` or `coin_rewards`. Design, the four-word model, the visibility and participation rules, the manual walkthrough and residual risks: `docs/handoff/task-06-guild-projects.md`, with the model in `docs/GUILDS.md`.
